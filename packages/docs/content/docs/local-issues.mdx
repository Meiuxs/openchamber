# Local issues

Local issues are issues that live in your project as markdown files. Each issue is one file named `LOCAL-<n>-<slug>.md`, for example `LOCAL-7-fix-login-timeout.md`. The board reads and writes those files, an agent session can work on them with the same files, and git carries them with the rest of the project.

## Where issues live

Issues sit in `.issues/` inside the project by default. A project can use another directory with the per-project `issuesDir` setting in `settings.json`. The setting has to be a relative path that stays inside the project, and anything else falls back to `.issues/`.

## The Local tab

Open the [Issues and PRs board](/issues-and-prs/) and switch to the **Local** tab to see a project's issues. The tab is per project, like the rest of the board: the project picker beside the tabs decides which project's `.issues/` directory is listed, and switching it switches the issues. There is no all-projects list — `LOCAL-<n>` restarts at 1 in every project, so two projects can both have a `LOCAL-1` and only the project tells them apart.

The search matches titles, identifiers, descriptions, the grouping slug and labels. Pasting an issue file name or path, such as `.issues/LOCAL-7-fix-login.md`, opens that issue. The filter beside the search narrows the list by state and priority, and by grouping slug where the issues carry one: the menu lists every slug in the project, not only those of the issues already shown, so you can switch from one grouping to another without clearing the filter first.

The preview shows the description, the priority, the labels and the comments. File paths in a description, such as `src/auth.ts:42`, render as links that open the file at that line. An issue with a `feature` value shows it, and **Blocked by** lists the issues it waits on — each opening that issue — and is where that list is changed: open it to pick from this project's unfinished issues, and unpick one to stop waiting on it. The list marks a row whose blockers still hold as **Blocked**. **Assignee** shows who owns the issue, and is where that is set too: pick a name the project already uses or type a new one, and unpick it to leave the issue unassigned. A local project has no member list, so the value is a plain name, not an account.

From the preview you can:

- **Create an issue** with a title, a description, a priority, labels and a grouping slug — picked from the slugs already in use, or typed as a new one. The board picks the next free `LOCAL-<n>` number and creates the file. A local issue always has a priority: the form starts at `low` and offers no “none”, and a file written with `priority: null` (an older one, or by hand) reads back as `low` and is saved that way the next time it is edited.
- **Edit** the title, description, priority, labels and grouping slug of an issue, and change which issues it waits on from the **Blocked by** row, which offers this project's unfinished issues instead of asking for a number.
- **Delete** an issue from the edit dialog's **Delete issue** button: it asks once more, then removes the file from `.issues/`. Anything that waited on it stops being blocked, and git can bring the file back if the delete was a mistake.
- **Change the state** from the status pill. The six states are `triage`, `backlog`, `todo`, `in-progress`, `done` and `canceled`; the board shows them in your interface language, while the file always stores the slug.
- **Assign an issue** from the **Assignee** row: the names the project already uses are offered, and a new one can be typed. Clearing it removes the field from the file, so an unassigned issue is one whose file says nothing about an owner.

Every change the board makes lands in the file right away, and a file you edit in your own editor shows up on the board on the next scan.

## Sharing an issue

A local issue lives in one project on one machine, so its link opens it in OpenChamber rather than on a website. The preview's **Copy in-app link** button copies this app's own address with the issue in it:

```
<your OpenChamber address>/?reference=https%3A%2F%2Fopenchamber.local%2Ftracker%2Flocal%2FLOCAL-7
```

Open that link and the issue's preview is on screen, in the same instance the link came from. The `openchamber.local` address inside it is not a page and nothing serves it; the board's search and a session's links recognise it, which is what a pasted `https://openchamber.local/tracker/local/LOCAL-7` is for.

Issues also travel as files: a teammate who clones the project sees the same `LOCAL-7` in their own instance, and can open it there.

## Grouping and blockers

Two optional frontmatter fields group issues and order the work:

- `feature: login` puts an issue under a grouping slug. The board filters by the slugs its issues carry, offers them in the filter menu, and shows the slug in the preview.
- `blockedBy: [LOCAL-4, LOCAL-6]` names the issues this one waits on. The issue counts as blocked while any of them is neither `done` nor `canceled`, and stops being blocked by itself when the last one settles; nothing is written to the waiting issue.

An identifier with no file behind it blocks nothing, and an issue never blocks itself. Both fields can be set and cleared from the board's create and edit dialogs, and by an agent editing the file.

## Session comments

In Settings under Integrations, the Local card has a **Session comments** switch. When it is on, a session attached to an issue adds a comment to the file when it starts, completes or fails. Each comment is a `### <date> · session <id>` entry under the issue's `## Comments` heading. The switch is on by default.

## Let an agent work on issues

Two built-in composer commands ship with OpenChamber — no setup, available in every project:

- `/local-issues` creates, finds, updates and deletes issues. The agent numbers new issues after the highest one it finds, changes state through the frontmatter, and appends the file paths it touched to the issue body so they link in the preview. The command tells the agent to keep the `## Comments` section as it is.
- `/issue-work` drives the assigned issues toward a fix: it proposes a menu of candidates ordered by priority, checks for work already in flight, refuses to fix without a verified mechanism, and closes the loop with comments and a `done` state once the proof passes.

Both accept an argument after the command name — `/local-issues create a login retry bug`, `/issue-work sync` narrows the menu to sync issues. The prompts live in Settings under Magic prompts (Session group), where each deployment can override the wording per project or globally.

## Triage roles

If you use the docs/agents issue-tracker convention, its five roles map onto states and labels: needs-triage moves an issue to the `triage` state, needs-info adds the `needs-info` label, ready-for-agent moves it to `todo`, ready-for-human moves it to `backlog`, and wontfix moves it to `canceled` with the `wontfix` label.

## Editing issues by hand

An issue file is plain markdown with a frontmatter block, so you can edit it in any editor. Two things to keep:

- The `identifier` in the file name is permanent. A file whose frontmatter identifier disagrees with its file name is skipped by the board, so never rename an issue file.
- The board rebuilds the `## Comments` section in normalized form whenever it appends a comment. Content below a second `## ` heading inside that section is dropped on the rebuild. Everything above `## Comments` survives as it is.

## Issues travel with the project

Issue files sit in the project directory, so they are project content: git tracks them, and a `git push` takes them to the remote with everything else. A fresh clone has its issues back as soon as the board scans the project.
